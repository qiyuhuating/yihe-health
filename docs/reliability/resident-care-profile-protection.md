# 长者联系方式与照护档案保护（实施中）

本项接续 P0-06/07，基线 `c46036b`。七列明文缺口已先用实际 handler 和隔离数据库复现；当前实现已加入认证加密、原有消费者适配、显式回填和轮换登记。工作树扩展回归为 47 个用例及子用例通过、0 失败、0 跳过，提交后的准确 SHA 验证另存，不据此宣称业务库已迁移或全部 PII 已保护。现有 PR 的社交改造仍保留其独立测试和 CI 失败/修复记录。

## 已核验字段与消费者

| 字段 | 分级及现有用途 | 适配边界 |
| --- | --- | --- |
| oldperson.phone | S3 联系方式；档案编辑/展示、设备列表、家属创建时按电话关联 | 需要可恢复密文和非唯一 HMAC 查询索引，不能移除关联功能 |
| oldperson.room | S3 可关联居住信息；档案编辑/展示 | 已核验生产源码没有以该列过滤或排序 |
| oldperson.illness、warn、food_like、food_hate、drag | S4 照护/病情/禁忌/用药信息；档案编辑/展示 | 保留授权明文响应、字段对应及长度，不与遥测统计 JSON 混用 |

写入：`handlers/handler_old_person.go`。档案读取：`handlers/old_person_query.go`。
另有 `familyrepo.loadBindingTarget` 的 `WHERE phone=? ... LIMIT 2 FOR UPDATE`，以及
`devicerepo.ListAdminDevices` → `handlers.adminDeviceView` 展示长者电话。
只修改档案列表会破坏这两个消费者；姓名搜索、年龄计算、绑定 ID、归属、设备状态与健康统计保持原有结构。

`phone` 原接口仅限制 12 字符，允许固定电话、空值等；本项不擅自改成账号的 11 位手机号规则。
`utf8mb4_bin` 的旧 VARCHAR 比较忽略尾随 ASCII 空格。HMAC 的比较输入只移除尾部 ASCII 空格，
保留原始值用于解密展示；回归必须证明旧 SQL 与新索引对相同数据的匹配一致。
长者共享电话号码是允许的历史语义，索引不能加唯一约束；两条匹配仍应返回原有歧义冲突，不能任选一条。

## 结构与事务

- 追加扩展迁移：`care_profile_cipher`、`phone_lookup`、`care_profile_protected`，以及独立的 resident lookupKey 指纹记录。
- 将七个可空字符串按固定 v1 结构封装，使用 `resident-care-profile:<old_id>` 认证 scope。NULL 与空字符串区别保留；JSON 版本、字段与长度均验证，明确要求认证密文前缀；现有 `securestore.Open` 同样严格拒绝无前缀输入。
- 仅对联系方式建立独立域 HMAC，保留必要的精确查询；其他六列当前没有查询需求，不额外增加可关联索引。读取时验证解密值与 phone_lookup 对应，错行密文、错 lookupKey、混合旧列、丢失元数据均拒绝。
- 在原有监护人/管理员权限及设备行锁事务内保留所有业务写入。先取得长者 ID，再封装敏感数据；配置密钥的新写入不临时写明文。失败回滚整次档案、元数据和归属变更。
- 列表/详情仍先通过现有实时职责授权，再认证和返回原字段；任一行认证失败，不返回部分明文列表。设备与家属关联路径同样适配，不能把 NULL 旧列直接当成“没有电话”。
- 只读路径不创建 key binding。保护行尚存而 ledger 缺失，不允许静默重新绑定；已有 ledger 时验证指纹，避免每次普通请求扫描整个历史表。

## 回填与轮换验收

`go run ./cmd/protect-resident-profiles` 默认 scan，`--apply --limit 100` 显式回填，使用现有 `MYSQL_DSN_FILE` 与 `DATA_ENCRYPTION_KEY_FILE` 注入配置；scan 也需要密钥以认证已有保护行。每次 1–1000 行和两分钟期限，完整预检后逐行锁定/重读；
要求停相关写入并验证可恢复备份。原 NULL/空值、记录数、电话歧义、查询分页和 API 字段保持一致。
取消/限量后的部分提交明确报告，重跑幂等；不清除或合并重复电话。列/ledger 回退脚本保留扩展，禁止自动明文降级。

新增密文为 rekey-data 的第 24 个目标，在同一 scope 重封装，HMAC/指纹及业务关系不变；通过实际 API 验证仅新 reader
仍可读、关联与编辑，不授权全资产密钥退役。8 个新增真实数据库根用例列入完整 CI 必需结果审计，另有纯密码/格式负例；全量 CI 的缺失或意外 skip 不算成功。

实际更新档案会先在行锁内认证旧值，再保存新值；错误 AEAD key 不能通过重写档案掩盖损坏。在线写入和回填均在长者行锁之前取得 key binding，保留原管理员权限及监护人锁顺序。创建先预留不含七列明文的 ID；存储故障回滚新档案和此前的名称等普通字段更新。

## 出生日期保护

迁移 `0040_resident_birthdate_protection.sql` 新增出生日期密文和保护标记。配置数据密钥后，新增和修改档案时在原事务内使用 `resident-birthdate:<old_id>` 认证加密，将原 `bothdate` 列置为 NULL。更新在行锁内先认证已有日期。数据库约束拒绝同时为已保护的记录保存原日期和密文。

管理员的档案列表和关联详情继续返回原日期字段并按当天计算年龄。无日期的历史档案保留原有年龄回退。设备和家属关联使用原权限、电话索引及关系字段；这两条路径无需解密日期。日期不参与查询条件，未增加索引。

从后端模块目录构建 `go build -o protect-resident-birthdates ./cmd/protect-resident-birthdates`，用私有的 `MYSQL_DSN_FILE` 和 `DATA_ENCRYPTION_KEY_FILE` 提供部署配置。默认只读验证已有日期及密文。回填前停用相关写入端，核对部署密钥并验证匹配的备份可恢复，再执行 `protect-resident-birthdates --apply --limit 100`。每轮最多迁移 1–1000 条，部分完成返回剩余量及非零状态，重跑保留已完成行。空日期保持 NULL。异常历史日期使回填在写入前停止，需先核对来源。

出生日期密文已纳入 `rekey-data`。回退 SQL 保留密文；如需回退到旧版应用，先恢复与旧版匹配的备份并核对切换后的业务变更。姓名、性别、派生年龄等其他身份资料、原始健康样本、历史备份和投影仍须按原验收要求处理。
