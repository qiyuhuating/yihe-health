# 评论与点赞手机号保护：适配设计（实施中）

本项接续 P0-06/07，基础版本为 `0bcc708`。已适配配置密钥的新评论/点赞写入、兼容历史读取、显式回填命令和密钥轮换登记。实现仅在配置密钥时保护新写入，不会在启动迁移时自动改写历史手机号；功能测试也不代表生产历史资产已迁移。验证完成前保留在本地工作树，不扩充 PR 的已验证范围。

## 已核验的行为

- `socialworkflow.CreateComment` 在事务内用作者手机号查当前家属头像、锁图片，再调用 `socialrepo.InsertComment` 写评论。保护写入必须在头像查询之后，保留图片引用事务。
- `socialrepo.ListComments` 查询作者手机号，返回前调用 `maskPhone`。`saidPhone` 继续是原有掩码或 null，不能把密文或完整手机号传给前端。
- `socialrepo.ToggleLike` 先锁父评论，再增删当前手机号的点赞行并修改 `said.nice_count`。查询中的 `good` 必须与同一套身份匹配条件一致。
- 评论回复/审核查询不返回手机号；目前源码中未发现其他评论作者手机号消费者。公告通知使用家属主账号联系方式，不能改成解密评论作者手机号发送通知。

对应源码：`internal/socialrepo/comments.go`、`comment_read.go`、`announcement.go`、`internal/socialworkflow/comments.go`、`internal/handlers/handler_social.go`（均位于后端）。

## 数据结构与密码边界

新增扩展迁移，保留旧列供尚未回填的历史记录读取：

| 表 | 新增信息 | 新写约束 |
| --- | --- | --- |
| said | 作者手机号密文、protected 标志 | 已配置密钥时 legacy 列为 NULL；密文以评论 ID 绑定 AEAD scope |
| nice_count | 手机号 HMAC 精确索引、protected 标志 | 已配置密钥时 phone 为 NULL；同一评论的当前查看者查询及取消点赞均按相同 HMAC 匹配 |
| 独立保护元数据 | 版本和 lookupKey 指纹 | 指纹先绑定后写入；不记录 key 本身 |

评论作者密文使用独立 `social-comment-phone:<said_id>` scope；不得复用账号 scope 或一个全表固定 scope。先在同一事务中取得 ID，再写密文；任何封装或持久化失败回滚，期间不插入临时明文。

点赞手机号只用于相等判断，不需恢复手机号，使用独立 `social-like-phone` HMAC 域。它仍是可关联的敏感元数据，不是匿名数据。禁止使用裸 SHA、手机号后四位或直接扩大旧列存储明文。lookupKey 轮换需要独立重建/兼容流程，不能随 AEAD key 切换。

元数据校验必须覆盖社交表自身：不能仅因 users/family 保护记录为空就重新绑定 lookupKey。保护记录尚存而指纹缺失、指纹与当前 key 不同、混合明文/保护标记不一致、评论密文换行或损坏均拒绝操作。未配置 key 时，只允许一致的历史未保护模式，不把损坏密文当明文。

protected 评论还必须明确要求受支持的认证密文格式。当前 `securestore.Open` 已严格拒绝无密文前缀输入；评论读取另行检查前缀、行标志和旧列一致性，缺少前缀、未知版本或 legacy 列非 NULL 都拒绝。点赞 protected 标志与索引缺失/格式错误同样不能回退到旧 phone。

## 查询、写入与兼容

1. 新建评论延续原事务与头像归属校验，保护失败不得留下评论或图片引用。
2. 评论读取先认证密文，再应用现有掩码；历史未保护记录保持原输出。错误时整次请求失败，不先返回部分评论。
3. 点赞查询和切换同时支持“一致的历史 phone”与“一致的 protected HMAC”；同一手机号在回填前后代表同一投票身份。绑定 key 错误时不能悄悄返回 good=0 或插入第二票。
4. 保持先锁父评论的顺序，再处理点赞行。迁移点赞行同样先锁父评论，避免与切换路径反向加锁。
5. 切换继续原手机号身份语义，不同时引入新账号/租户归属规则；账号改号、账号删除或跨角色相同手机号的产品规则另行设计。

## 历史回填、轮换与回退

- `go run ./cmd/protect-social-phones` 默认只读 scan；`--apply --limit 100` 显式回填，每次最多 1–1000 行、总时限 2 分钟。使用服务现有的 `MYSQL_DSN_FILE` 和 `DATA_ENCRYPTION_KEY_FILE`（单 key/keyring 均可），不通过命令行提供秘密。scan 也需要密钥，以认证已有保护数据。只打印聚合计数，不输出手机号、密文或 key。
- apply 前停止所有评论、点赞及其删除写入，并验证备份能恢复；完整预检先于任何修改。每行独立事务、条件更新及锁内重新读取，不将批次事务误作覆盖整个库的停写屏障。超限/中断可能已提交部分行，保持屏障并重跑；未完成时返回非零和 `complete=false`，不能作为成功上线凭据。
- 无效历史手机号、重复投票、混合元数据和认证失败应列为阻断项，不自动丢行或改点赞计数来满足唯一约束。
- 存在身份的孤立点赞、待迁移点赞所在评论的聚合计数异常也阻断回填。旧手机号为 NULL 的记录保留为未署名记录，不制造手机号；`complete` 只表示本项范围内的非 NULL 手机号副本已清空，不代表每行均有可恢复身份。评论主动删除在父行锁内同时清除点赞，避免留下新的孤立身份。
- 回填后原始手机号列清空，记录数、评论响应、点赞身份和聚合计数保持一致。中断重跑幂等；并发删除/切换不被旧扫描结果覆盖。
- 评论密文加入 rekey-data 的注册清单，保持 row scope；点赞 HMAC/指纹不因 AEAD 轮换改变。移除旧 reader 后验证评论仍可读，不据此授权全部旧 key 退役。
- 旧二进制不理解新列，不能直接回退上线。回退需保留扩展列/ledger，在已验证备份和停写流程下恢复兼容版本；本项不提供自动明文降级。
- SQL dump、binlog、旧备份、历史投影和导出中的副本要单独盘点。当前两列回填成功不等于全库/全部历史资产完成保护。
