# 独立数据库迁移任务

颐和的发布镜像同时包含正常服务入口 `/app/yihe` 和独立迁移入口 `/app/migrate`。二者来自同一份源码和同一个不可变镜像，避免生产迁移依赖临时下载 Go 工具链或挂载源码。

## 执行顺序

1. 停止所有旧版本写入进程，备份目标 MySQL 8.4 和数据加密密钥，并确认迁移版本与应用版本兼容。
2. 在将要部署的同一镜像上运行 `/app/migrate`，注入受控的 `MYSQL_DSN`，等待进程成功退出。
3. 迁移成功后启动新版本 `/app/yihe`。涉及 0044–0051 的升级不得混合运行新旧写入进程；迁移失败时不得继续发布依赖新结构的应用实例。

容器环境可使用以下命令；网络参数和密钥注入方式由实际部署平台提供，不要把真实 DSN 写入源码、镜像或日志：

```sh
docker run --rm --entrypoint /app/migrate \
  --env MYSQL_DSN="$MYSQL_DSN" "$IMAGE"
```

Kubernetes Job 应将 `command` 设为 `["/app/migrate"]`，通过 Secret 注入 `MYSQL_DSN`，并由发布控制器等待 Job 成功后再继续应用 rollout。这里的入口覆盖只改变该迁移任务，不影响正常容器仍使用 `/app/yihe`。

## 保持不变的边界

- 迁移命令复用现有 `backend/cmd/migrate` 和 MySQL 迁移实现，包括数据库级执行锁、校验和、结构摘要、逐语句检查点及中断恢复；本次不另写迁移器。
- 单机服务仍保留启动时安全自动迁移。本入口使生产环境可以执行独立迁移任务，但不会自动禁用 API 自动迁移，也不替代具体的集群发布编排。
- 镜像回滚不会自动回滚数据库结构。数据库回退和恢复必须按照备份恢复流程单独执行。
- `cmd/migrate` 当前使用两分钟上下文超时；大型迁移的容量验证和执行预算仍属于后续工作。

## 验证

`.github/workflows/p0-db-migration.yml` 构建完整发布镜像，确认默认入口仍为 `/app/yihe`，再用镜像内的 `/app/migrate` 对一次性 MySQL 8.4 连续执行两次迁移，并比较两次结构转储，验证第二次为无操作。

该工作流验证的是实际发布产物，而不是源码目录中的 `go run`。迁移锁的并发语义和中断恢复仍由现有 Go/MySQL 测试覆盖；不能把两次顺序执行描述成完整的多实例并发或故障中断验收。
